# SPEC：行政區醫療院所查詢功能

> 本文件保存 2026-10-12 的原始規格與驗收。2026-10-15 已依新的 Schema 整合規格改為在 neo4j 透過 HAS_FACILITY 查詢醫療院所，並支援實際科別；現行定義見 [整合 Schema](neo4j-integrated-schema.md) 與 [管理程序](neo4j-integration-operations.md)。本文件的舊資料庫分工及禁止合併條款不適用於本次已授權整合。

**專案：** Advanced_DB_Project（臺灣醫療資源分析系統）  
**功能名稱：** 行政區查詢  
**狀態：** 已實作並通過功能驗收（2026-10-12）  
**範圍：** 前端行政區查詢頁面、必要的後端 API、Neo4j 唯讀查詢

---

## 1. 功能目標

在網站左側側邊欄新增可正常使用的「行政區查詢」頁面。

使用者不需要撰寫 Cypher，即可透過縣市、鄉鎮市區及院所類型選單，搜尋指定行政區內的所有醫院與診所，並在互動地圖上查看院所位置及資訊。

本功能只負責行政區醫療院所搜尋，不包含醫療資源統計分析、導航、掛號或其他延伸功能。

## 2. 現有系統與資料來源

### 2.1 專案架構

- 後端使用 Java、Spring Boot。
- 前端沿用既有 HTML、CSS、JavaScript 架構。
- 地圖沿用「查詢分析」頁面已使用的地圖技術。
- 專案採功能導向資料夾結構，各頁面 HTML、CSS、JavaScript 分離。
- 共用模組集中於 `shared/`。
- 不得為本功能重新建立一套前端框架或資料庫連線架構。

### 2.2 Neo4j 資料庫

目前有兩個獨立的 Neo4j 資料庫：

**`medicalfacilities`**

儲存個別醫療院所，已確認節點 Label 為 `MedicalFacility`。

已知屬性包含：

- `name`：院所名稱
- `type`：院所類型
- `address`：院所地址
- `phone`：電話
- `latitude`：緯度
- `longitude`：經度

實作前仍須檢查實際 Schema 與屬性型別。

**`neo4j`**

儲存行政區、醫事人員、科別、人口密度、所得等統計資料。

本次功能不需要跨資料庫建立關係，也不需要使用統計資料推算個別院所。

兩個資料庫必須維持獨立。

### 2.3 行政區 CSV

專案 `data/` 資料夾已放置臺灣行政區 CSV。

請先檢查檔案內容與欄位，再使用其中的縣市及行政區名稱建立下拉式選單。

要求：

1. 不得手動硬編碼全臺行政區清單。
2. 縣市選單必須使用 CSV 的實際資料。
3. 鄉鎮市區選單必須根據選取縣市動態更新。
4. 如果 CSV 包含行政區代碼，應優先使用代碼作為選單內部識別值。
5. 不得因不同縣市存在同名行政區而混淆查詢。

## 3. 功能需求

### FR-01：縣市選擇

提供縣市下拉式選單。

- 初始狀態未選取。
- 選項來自行政區 CSV。
- 不得出現重複縣市。
- 切換縣市時，清除先前選取的鄉鎮市區。

### FR-02：鄉鎮市區選擇

提供鄉鎮市區下拉式選單。

- 尚未選擇縣市時不可選取。
- 選取縣市後，只顯示該縣市所屬行政區。
- 不得混入其他縣市的同名行政區。
- 搜尋時必須同時考慮縣市及鄉鎮市區。

### FR-03：院所類型篩選

提供三種選項：

- 全部（預設）
- 醫院
- 診所

分類規則：

- 醫院：`n.type CONTAINS '醫院'`
- 診所：`n.type CONTAINS '診所'`
- 全部：符合上述任一條件

「全部」不包含病理中心等其他類型。

不得使用 `n.type = '診所'`，因為原始資料包含多種細分類型。

### FR-04：執行搜尋

提供明確的搜尋按鈕。

- 縣市及行政區皆已選取才能搜尋。
- 搜尋時顯示載入狀態。
- 搜尋完成後顯示符合條件的院所總數。
- 無結果時顯示「此行政區沒有符合條件的醫療院所」。
- 發生資料庫或 API 錯誤時，顯示錯誤提示，不得偽裝成 0 筆結果。
- 不得使用假資料代替 Neo4j 查詢結果。

### FR-05：搜尋結果

搜尋結果至少包含：

- 院所名稱
- 院所類型
- 地址
- 電話（有資料時）
- 經緯度（有資料時）

可使用簡單的結果列表搭配地圖，不需要額外設計複雜的資料分析儀表板。

### FR-06：地圖標記

沿用目前網站的地圖元件。

- 查詢成功後顯示符合條件的院所標記。
- 點擊標記開啟資訊視窗。
- 資訊視窗顯示名稱、類型、地址、電話。
- 地圖自動調整至搜尋結果範圍。
- 重新搜尋時移除上一輪院所標記。
- 不得讓不同查詢結果的標記混在一起。
- 缺少有效經緯度的院所仍計入結果總數，但不顯示無效標記。
- 須顯示無法定位的院所數量。
- 如果既有地圖支援標記聚合，可沿用；不得為此引入大型新依賴。

### FR-07：地址與行政區比對

院所地址可能存在格式差異，必須先檢查實際資料。

至少考慮：

- `台` 與 `臺` 的差異。
- 縣市與行政區的完整名稱。
- 地址開頭是否有郵遞區號或空白。
- 同名行政區不能跨縣市混淆。

不得僅使用行政區名稱進行模糊比對，例如不能只用 `CONTAINS '東區'`。

如果需要地址正規化，應在應用程式查詢層處理，或先提出資料調整方案，不得擅自修改原始 Neo4j 節點。

無法確定行政區歸屬的資料不得任意分配到某個行政區，必須回報。

## 4. 資料庫查詢規範

### 4.1 全國分類基準

已在 `medicalfacilities` 資料庫實際執行以下查詢。

**診所：**

```cypher
MATCH (n:MedicalFacility)
WHERE n.type CONTAINS '診所'
RETURN count(n) AS total;
```

**預期結果：22,742**

**醫院：**

```cypher
MATCH (n:MedicalFacility)
WHERE n.type CONTAINS '醫院'
RETURN count(n) AS total;
```

**預期結果：483**

這兩個數字為本次功能的固定測試基準，合計 23,225 筆醫院及診所資料。

其餘 13 筆為病理中心，不納入本功能的「全部」篩選。

### 4.2 查詢實作要求

1. 使用 `MedicalFacility` Label，不得使用不限定 Label 的全資料庫掃描作為正式查詢。
2. 使用參數化 Cypher，不得直接拼接使用者輸入。
3. 不得在正式查詢中加入未經要求的 `LIMIT 50`、`LIMIT 100` 等截斷條件。
4. 若資料量較大，可使用分頁或分批載入，但必須能取得全部符合條件的資料。
5. 查詢總數應由資料庫實際計算，不得使用目前已載入的標記數量冒充總數。
6. 所有查詢必須為唯讀，不得修改或刪除節點及關係。
7. 不得直接將使用者輸入的 Cypher 當成行政區搜尋 API 執行。

### 4.3 行政區查詢驗證

至少以「新竹市 → 香山區」作為測試案例。

分別測試：

- 全部醫院與診所
- 只有醫院
- 只有診所

須使用獨立 Cypher 查詢比對 API 回傳總數。

全國分類總數符合預期，不代表行政區搜尋已經完整；行政區搜尋仍須單獨驗證。

## 5. 頁面設計與整合

### 5.1 頁面位置

使用現有側邊欄中的「行政區查詢」項目。

此頁面應獨立於「查詢分析」，但視覺風格必須一致。

建議版面：

- 左側：縣市、行政區、院所類型選單，以及搜尋結果列表。
- 右側：互動地圖。

可依現有版面調整比例，但不得自行重新設計整個網站。

### 5.2 程式結構

- 新功能放入獨立頁面資料夾。
- HTML、CSS、JavaScript 分離。
- 共用地圖功能優先沿用 `shared/` 中的模組。
- 後端沿用現有 Controller、Service、Repository 的設計風格。
- 不得把所有功能塞進 `pages/query/index.html`。
- 不得新增功能重複的 Service 或資料庫連線設定。

### 5.3 既有功能保護

以下功能必須保持正常：

- 查詢分析頁面
- Cypher 編輯器
- 條件篩選
- 查詢結果表格
- CSV 下載
- 現有地圖標記與互動

不得為完成行政區查詢而破壞既有功能。

## 6. 非功能需求

### NFR-01：資料完整性

必須能查詢所有符合條件的院所，不得靜默忽略資料。

### NFR-02：效能

優先使用現有技術與資料庫索引。若需要新增索引，先說明原因與建議，不得擅自修改資料庫。

### NFR-03：錯誤處理

至少區分：

- 尚未選擇必要條件
- 查詢結果為空
- API 請求失敗
- Neo4j 連線失敗
- 院所缺少有效座標

### NFR-04：維護性

避免重複程式碼、硬編碼行政區與大型單一 JavaScript 檔案。

10. 未確認既有實作就建立重複模組。

## 9. Codex 執行流程

請依序執行：

**階段一：現況檢查**

閱讀專案結構、行政區 CSV、資料庫設定、既有地圖模組與後端程式。

確認實際資料結構與本 SPEC 是否一致。

**階段二：實作**

只實作行政區查詢頁面與必要 API，沿用既有架構。

**階段三：驗證**

執行第 7 節驗收測試，特別檢查 22,742 筆診所與 483 筆醫院的分類基準，以及行政區查詢的完整性。

**階段四：交付報告**

完成後提供：

- 新增及修改的檔案清單
- API 路徑與參數
- Neo4j 查詢邏輯
- 各項驗收測試結果
- 未通過項目及原因
- 已知限制

不得將尚未實際執行的測試標記為通過。

若遇到規格未定義、資料結構衝突或需要大幅修改既有架構的情況，應先提出問題，不要自行擴充需求。

# Neo4j 醫療資源分析系統－Codex 測試規格

## 一、測試目標

請根據目前專案架構，為行政區醫療資源統計查詢功能建立自動化測試。

本次以**測試既有功能**為主，不要為了通過測試而新增不相關的頁面、修改資料庫內容、虛構地理座標或重新設計系統架構。

### 測試資料庫

資料庫：`neo4j`。行政區為 `鄉鎮區碼與名稱`，368區。

正式節點：`綜合所得`、`人口與土地`、`醫療院所統計`、`醫事人員類別`、`科別`。
正式關係：`RECORD_INCOME`（統計年112）、`RECORD_POPULATION_AND_AREA`（統計年114）、`RECORD_MEDICAL_FACILITIES`（統計年114）、`RECORD_PERSONNEL`、`RECORD_DEPARTMENT`。
年度取自關係，不是統計節點。人員及科別數量取自關係的`數量`，醫院／診所以`類型`區分。
科別數量是提供該科別的院所家數，不得加總所有科別作為院所總家數。
院所總家數及總人力取自`醫療院所統計.院所家數`、`醫事人員總計`。

### 測試分類

**A. 固定資料驗收（Snapshot Test）**

使用目前 Neo4j 資料庫的實際查詢結果，驗證筆數、指定行政區及已知欄位數值。當資料更新時，應重新建立預期結果。

**B. 邏輯驗收（Logic Test）**

驗證條件篩選、數值計算、關係加總、缺值處理、排序及錯誤處理。應使用可控制的測試資料或測試替身，避免完全依賴目前資料庫內容。

不得只檢查 API 是否回傳成功；必須驗證結果是否符合業務邏輯。

### TC-08：三類醫師與每萬人口西醫師數

使用`RECORD_PERSONNEL`，各區分別回傳西醫師、中醫師、牙醫師的醫院／診所／合計人數。
人口取`RECORD_POPULATION_AND_AREA`（114年），預期368個唯一行政區。
每萬人口西醫師數 = round(10000.0 * 西醫師合計 / 人口, 2)。人口0或缺值為null。
排序：每萬人口西醫師數降冪，無自動次要排序。

不要把三類合計當成西醫師數，也不得將護理師等其他人員算入醫師。
既有API `doctors/doctorRate` 仍表示三類醫師合計及其人均值；新增`westernDoctors/westernDoctorRate`表示西醫師。

- [ ] 368區且代碼不重複，不漏零值區。
- [ ] 三類各自醫院＋診所正確加總。
- [ ] 鳥松指定數值吻合。
- [ ] 不因多條關係重複加總，缺特定類別按0。
- [ ] 西醫師人均公式、零／缺人口及排序正確。

## 三、通用查詢邏輯測試

### 1. 行政區範圍

- [ ] 全國查詢。
- [ ] 指定縣市查詢。
- [ ] 指定單一行政區查詢。
- [ ] 不同縣市的同名鄉鎮區不得混入。
- [ ] 行政區名稱及縣市名稱應正確對應。
- [ ] 查詢單一行政區時，不得混入其他行政區數值。

### 2. 數值條件

- [ ] 真實資料的最小值與最大值。
- [ ] 下限等於上限。
- [ ] 條件超出資料實際範圍。
- [ ] 下限大於上限。
- [ ] 負數、小數、非數字等非法或特殊輸入。
- [ ] 多個不同條件採 AND。
- [ ] 省略條件代表不限制。
- [ ] 數值 `0` 不等於未填寫。
- [ ] 切換條件後不得沿用已清除的篩選值。

### 3. 人員與科別

- [ ] 人員類別選單正確載入資料庫的類別。
- [ ] 科別選單正確載入資料庫的類別。
- [ ] 醫院、診所、合計三種統計模式。
- [ ] 指定人員類別時，只加總對應 `RECORD_PERSONNEL` 關係。
- [ ] 指定科別時，只加總對應 `RECORD_DEPARTMENT` 關係。
- [ ] 同一行政區不得因多條關係而重複出現。
- [ ] 同時使用不同一對多關係時，不得因資料列倍增造成重複加總。
- [ ] 不存在的類別應回傳明確的空結果或輸入錯誤，不得誤回傳全部類別。

### 4. 缺值處理

- [ ] 缺少醫院統計節點時，依已確認的資料規則按 0 處理。
- [ ] 缺少診所統計節點時，依已確認的資料規則按 0 處理。
- [ ] 缺少特定人員或科別關係時，依統計規則按 0 處理。
- [ ] 所得缺值不得冒充 0。
- [ ] 人口缺值不得冒充 0。
- [ ] 面積缺值不得冒充 0。
- [ ] 人口為 0 時不得進行除以人口的計算。

### 5. 查詢結果與錯誤

- [ ] 回傳真實總筆數，不得以分頁筆數冒充總筆數。
- [ ] 空結果有明確提示。
- [ ] 無效請求有合理錯誤訊息。
- [ ] 資料庫斷線時，前端不得顯示為查無資料。
- [ ] 查詢逾時有明確處理。
- [ ] 不得因查詢失敗而繼續顯示過期結果並誤導使用者。

### 6. 前端互動

- [ ] 查詢條件切換正確。
- [ ] 查詢期間顯示載入狀態。
- [ ] 查詢完成後正確顯示表格。
- [ ] 表格數值排序正確，不得使用字串排序取代數值排序。
- [ ] 使用者快速連續查詢時，舊請求不得覆蓋最新結果。
- [ ] CSV 下載資料與目前查詢條件一致。
- [ ] CSV 下載保留正確欄位與數值。
- [ ] CSV 匯出不得因特殊字元造成欄位錯位或試算表公式注入。

### 7. 資料安全

- [ ] 搜尋功能全程唯讀。
- [ ] 不得執行 CREATE、MERGE、SET、DELETE、DETACH DELETE 等資料修改操作。
- [ ] 不得修改既有節點、關係或屬性。
- [ ] 使用者輸入不得直接拼接成不安全的 Cypher。
- [ ] 應使用參數化查詢與適當的後端輸入驗證。
- [ ] 測試過程不得污染正式 Neo4j 資料庫。

## 五、測試執行要求

請先閱讀現有專案程式碼、查詢 API、資料存取層與測試架構，再決定適合的測試位置。

1. 優先沿用現有測試框架，不要為了測試重構整個專案。
2. 將固定資料驗收與邏輯驗收分開，避免測試過度依賴特定年度的正式資料。
3. 需要連接 Neo4j 的固定資料測試，應明確標記為整合測試；無資料庫環境時可跳過，但必須回報跳過原因。
4. 邏輯測試應盡可能使用可控制的資料，包含零值、缺值、多條關係及邊界條件。
5. 不得為了讓測試通過而修改正式資料或調整預期數值。
6. 保留現有查詢排序規則，不擅自新增次要排序條件。
7. 不要將尚未取得資料的地圖功能列為本次必須通過的項目。
8. 若發現現有實作與規格不符，先記錄差異與原因；不要擅自擴大修改範圍。
